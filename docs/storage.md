# Source snapshot storage (schema 1)

`contextforge init` creates configuration; `contextforge index` explicitly captures supported UTF-8 source files. CLI status and doctor inspect existing metadata read-only. MCP tools never create or refresh an index.

Cache path is `<index_root>/<sha256(native-canonical-root)>/index.sqlite`. A relative index root is beneath `.contextforge`; an absolute root explicitly selects external metadata storage. Canonical root identity is platform-local, not a portable repository identifier. Moving a repository creates a different cache namespace. Repository identity is also checked inside the database.

SQLite uses bundled SQLite through rusqlite 0.41.1, parameter-bound values, a 2-second busy timeout and `trusted_schema=OFF`. Every update uses one immediate transaction. Source discovery and reads happen before that transaction. All eligible files are read and SHA-256 hashed; only added/changed records are written. No timestamp-only shortcut can miss a same-length edit. Deleted/ignored/renamed files lose obsolete rows (rename is delete+add). This is incremental database writing, not incremental source reading or parsing.

Schema 1: `repository(singleton, identity)` and `files(path, language, fingerprint, content, bytes)`. Paths are relative. `PRAGMA user_version=1`; only an empty version-0 database migrates to 1, transactionally. Unknown versions/nonempty unknown schemas/corrupt databases fail without being deleted or rebuilt. Future symbols/relations/FTS need explicit migrations, not placeholder tables. Existing database contents are local cached evidence, not trusted operational instructions.

Discovery cap: 1000 eligible files, 10000 yielded entries and depth 64. Total snapshot text cap: 64 MiB; per-file cap: configured maximum (default 1 MiB, maximum 16 MiB). Truncation and read failures prevent all database updates, so a partial inventory cannot delete undiscovered records. A changing file that becomes missing/binary/oversized during capture aborts the snapshot. Files may change after capture; this is a snapshot, not a live index. Status explicitly says `freshness: "not_checked"` until a future validity check runs.

Indexing stores source bodies, potentially including source-embedded secrets, locally. Do not share cache directories. Newly created cache directories use mode 0700 on Unix; Windows inherits directory ACLs. Existing permissions are not rewritten. Never include metadata in public fixtures/commits. Symlinks/reparse points are rejected for cache directories/database/known SQLite sidecars and every source path component. Handle-relative race protection, existing hard-link detection, hostile-cache schema tampering, database size/query-step limits and cross-platform permission verification remain hardening work. Do not use actively hostile repositories or attacker-controlled caches.

Regression tests cover cold/unchanged indexing, same-size edits, deletion/rename, newly ignored/binary files, persistence, concurrent writers, rollback on an injected write failure, abrupt writer-process exit, future versions, corruption, truncation and external-cache repository isolation. The next explicit index can recover SQLite's interrupted rollback journal; read-only status does not promise hot-journal recovery. A generated public 100-file Rust fixture supplies a reproducible [local baseline](benchmarking.md); these results are not a general performance claim.
